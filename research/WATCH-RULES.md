# 更新エージェントの判断基準（WATCH-RULES）

`/update-wiki` で記事を更新するエージェント向けの基準です。検知は `npm run watch`（LLM なし）が行い、レポート `research/watch/report-YYYY-MM-DD.md` を出力します。エージェントはレポートの「推奨アクション」の順に処理します。調査・執筆の共通ルールは `research/RESEARCH-RULES.md`、記事の書式は `content/SCHEMA.md` に従います。

## 1. 直すもの・直さないもの

直す:

- 数値（必要 IL、費用、回復量、上限、確率）、日付、期間、状態（実装済み／未実装、開催中／終了）の変化
- 出典 URL のリンク切れ（代替出典へ差し替え、見つからなければその主張を外す）
- 出典の更新で本文が裏付けられなくなった主張
- 公式告知に基づく `news/` 記事の追加（2 章）
- レポートの「新トピック候補」のうち、`research/topic-inventory.md` に未掲載で、読者に必要なもの

直さない:

- 文体、構成、見出しの好みによる書き直し。影響記事は変更箇所だけを直す（全面書き直し禁止）
- 影響を受けていない記事（レポートに出ていない記事は開かない）
- 攻略サイトのティア表・評価・単一ユーザーの発言・噂（`unverified` は掲載しない）
- 韓国版のみの仕様を、グローバル版の記述として混ぜること
- ETag や Content-Length が変わっただけで、本文の該当部分に差が見つからない場合（広告・ビルド番号などの揺れ）。この場合は記事を変更せず、PR の「変更なし確認」に URL を 1 行書く

## 2. 公式告知（レポート ①）

1. `content/news/` に告知 1 件につき 1 記事を先に追加する（`category: news`、`confidence: official`、`sources[].kind: official`）。複数の告知が同じ話題なら 1 本にまとめてよい。
2. 次に、その告知で変わる記事を列挙する（メンテナンス日程、イベント期間、仕様変更、ドロップ・価格の変更など）。列挙した記事は 1 章の基準で差分だけ直す。
3. 告知が plaync など JS 描画のページの場合、本文の取得は `research/source-registry.md` の方法（curl など）を使う。取得できないときは、告知を転載した信頼できる 1 資料で `community` として書き、「要確認」を付ける。
4. 公式告知は、記事の根拠として最優先で使う。

## 3. 新トピック（レポート ②・③）

- `research/RESEARCH-RULES.md` に従って調査し、新規記事と `research/topic-inventory.md` の台帳行を同時に追加する。
- 新規記事の初週は `confidence: community` とし、本文冒頭に `> **要確認**：` を置く。
- DB バージョンが上がった場合は、DB に基づく数値を使っている記事を、レポートの影響記事リスト（出典 URL の変化）から確認する。DB 全体を再調査しない。
- 攻略サイトの新着は、題名から既存記事との差分があるものだけ開く。差分がなければ何もしない。

## 4. community から verified への昇格

次の条件をすべて満たしたときだけ `verified` にする。

- 独立した 2 つ以上の資料（DB と攻略サイト、または別々の攻略サイト）が一致している。同じ元記事の転載は 1 資料として数える。
- 記事内の主要な主張すべてが条件を満たしている（`confidence` は最も弱い主張に合わせる）。
- 昇格したら、本文冒頭の `> **要確認**：` を外し、`updated` と `sources[].date` を更新する。
- 公式で確認できたものは `official` にする。

逆に、出典がなくなった・食い違いが出た場合は、`confidence` を下げて「要確認」を付ける。裏付けが 1 つも残らない主張は外す。

## 5. 資料が食い違うときの優先順

1. 公式（NCSOFT の告知・公式サイト・プレスリリース）
2. Global DB（aion2.gaming.tools など）
3. 攻略サイト・ガイド

- 数値は上位の資料を採用し、下位の資料と食い違う場合は本文で「資料により異なる」と一言書く。
- 同順位の資料同士が食い違うときは、新しい日付の資料を採用せず、両論を併記して `community` にする。
- 韓国版の更新内容は、グローバル版での実装が確認できるまで本文に入れない。

## 6. 更新時に必ず直す項目

- 本文を変えた記事の `updated`（作業日）
- 根拠を取り直した出典の `sources[].date`
- 追加した記事の `related`（既存記事と相互にリンク）
- `根拠：[S01]` の参照が出典一覧と合っていること

## 7. トークンを使わないための規則

- 読むのは、レポートと影響記事だけ。リポジトリ全体や `content/` 全体を読まない。
- ページは `research/cache/`（git 管理外）に保存し、ETag を使って取得する。未変更（304）のページは再取得しない。
  - 例: `curl -sL -A "<ブラウザ UA>" -H "If-None-Match: <保存済み ETag>" -D <url ごとのヘッダー保存先> -o <本文の保存先> <url>`
  - `research/cache/` には本文と ETag を URL ごとに保存し、本文は `sed`/`grep` で必要な箇所だけ読む。
- 変更ページだけ取得する。レポートに出ていない出典 URL は取得しない。
- 最終報告は 300 字以内（変更記事数、新規記事、ゲート結果、PR 番号、要確認事項）。
- `state.json` は処理中に触らない。PR をオーナーが取り込んだ後に `npm run watch -- --commit-state` を実行する。それまでは未処理の変化が次回のレポートにも出る。

## 8. 検知の限界

- 検知は HEAD リクエストの ETag / Last-Modified / Content-Length だけを見る。検証子を返さないサイトは「検知不能」として件数だけ出る。
- `aion2.gaming.tools` は ETag がリクエストごとに揺れるため、Last-Modified / Content-Length のみで比較する。同じ長さのまま数値だけ変わる更新は検知できない。DB バージョンと sitemap の新規 URL を併用する。
- plaync 系（`aion2.plaync.com`、`lounge.plaync.com`、`aion2.ncsoft.jp`）は JS 描画のため取得せず、レポートの「要目視」に出す。公式告知（①）がある回に、関係する記事だけ確認する。
- 取得に失敗した信号は前回状態を保持し、レポート ⑤ に記録する。次回また取得できれば自動的に比較に戻る。
